## Declaring "Needs a Live Check" Before Building the Simulation

- [ ] Before telling the owner a live backend/end-to-end render is needed to verify a fix, check whether the repo already has (or could cheaply grow) a fully simulated harness for the layer in question — mocked network + websocket boundaries driving the REAL running app (Playwright `page.route`/`page.routeWebSocket`), a hook/component test with realistic mock data (vitest + `renderHook`/RTL), or a backend test that drives real dispatch code with only the true engine boundary mocked (R2). "Can't verify without a live render" is a conclusion to justify, not a default — build the harness first, and only ask for a live check for what's genuinely impossible to simulate (real model-load timing, real audio correctness, real hardware/GPU behavior). <!-- added 2026-07-05, source: user-flagged — after fixing the W-PAR active_segments_map bug, the fix was reported as "R1 revert-checked, but not observed in a live render — please re-run the visual check," when in fact a Playwright E2E test (page.routeWebSocket mocking the entire backend, driving the real ChapterEditor with a realistic active_segments_map frame) fully proved the visual behavior with zero live backend/TTS needed. The owner's exact words: "by the time a visual check is made there shouldn't be a question of if it will work but more of a how does it look to you." -->
- [ ] When building a full-app E2E simulation, budget for discovering the harness itself is stale/incomplete (missing route mocks, wrong wire-message format, wrong dev-server mode) — this is expected exploration, not a sign the approach is wrong. Concretely: check whether the test infra is even exercised by CI (a spec file absent from `.github/workflows/ci.yml` may have silently rotted); prefer the production-preview server (`vite build && vite preview`, matching CI) over the dev server for E2E runs, since dev-mode tooling (HMR sockets, Strict Mode double-invoke) can behave differently in ways unrelated to the app itself; and verify any raw message/event shape you inject against what the current wire protocol ACTUALLY handles (grep for the handler, don't assume an existing test's message shape is still live) before concluding the app itself is broken. <!-- added 2026-07-05, source: self-caught mid-simulation — chasing "the app's websocket never connects" burned significant effort before finding the actual causes: (1) a stale sibling test in the same file used a `{type: 'job_updated'}` message with no handler anywhere in the codebase, (2) the default `npm run dev`-based Playwright config differs from CI's `vite preview` production-build approach in ways that mattered, (3) a piece of MY OWN debugging instrumentation (a `window.WebSocket` monkey-patch via `page.addInitScript` that dropped the non-enumerable `OPEN`/`CONNECTING` static constants via `Object.assign`) silently broke the exact connection I was trying to observe -->
