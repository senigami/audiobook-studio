# Task 015 — Ambient On Air indicator

Status: pending

Risk: multi-file (needs render-progress state lifted out of Cast mode into the console-shell level — touches `useStudioChapter.ts`, a new `AmbientStatus/` component, and `DirectorsConsole/index.tsx` or `BookLayout.tsx`)

## Goal

Build the always-mounted, visible-from-every-mode render-progress pill described in `design-docs/workflows/chapter-editor-modes.md` §4: **"Ambient render pill (top bar): Idle → Queued → `Rendering 47% · ~3m` (arc) → Done (fades) → Error (sticks). Click for a non-modal segment-level popover. Visible from every mode — this is the answer to 'how do I see render progress when I'm not in a render context.'"**

## Why this matters

Today, render progress only exists inside Cast mode's own component tree. A user who paints assignments, switches to Booth (which task 014 makes silently queue a re-render), and stays in Booth has **no visible signal** that anything is rendering at all until they flip back to Cast — exactly the gap this indicator exists to close.

## Current shape (verified)

- **No `AmbientStatus/` folder exists anywhere** (confirmed via `find`). The design doc's §17 architecture diagram names it as a **sibling of `DirectorsConsole/`**, not nested inside it: `pages/ChapterEditor/components/AmbientStatus/` alongside `pages/ChapterEditor/components/DirectorsConsole/` and `.../ChapterSurface/`.
- **All render-progress state is currently computed inside `CastToolBody`** (`CastTool/index.tsx`), via `useStudioChapter()` (`frontend/src/pages/Book/studio/useStudioChapter.ts`, 1033 lines — already over both this repo's 500-line "candidate for splitting" and 600-line "should be refactored when touched" thresholds). `CastToolBody` resolves its own `activeChapterId` from `useSearchParams().get('chapter')` and `useBookDataContext()`'s `chapters`/`jobs` (lines 34-90), then calls `useStudioChapter({...})` and destructures (lines 105-112): `chapterRenderPendingSegmentIds`, `chapterRenderDoneSegmentIds`, `chapterRenderRenderingSegmentIds`, `chapterRenderQueuedSegmentIds`, `chapterRenderPreparingSegmentIds`, `chapterRenderRenderingBatchProgressById`. These feed `RenderControlsStrip` (`CastTool/index.tsx:402-418`, itself a re-export: `frontend/src/pages/Book/studio/RenderControlsStrip.tsx` → `ChapterScriptToolbar` in `frontend/src/pages/ChapterEditor/components/ChapterHeader.tsx`).
- **The human-facing label state machine the pill actually needs already exists, but one level deeper.** `ChapterHeader.tsx`'s exported `useChapterStatus` hook (line 16) computes exactly the Idle/Queued/Preparing/Rendering/Finalizing labels the design doc's pill describes (lines 33-51: `rawQueueStatus` ternary chain → `'Queued'`/`'Preparing'`/`'Rendering'`/`'Processing'`/`'Finalizing'`/`null`, held stable by `useQueueStatusHoldTimer`). `useStudioChapter.ts` calls it once (line 655) with `chapter`, `job`, `generatingSegmentJob`, and derived flags/counts, and returns the result as `status` — this is what `ChapterScriptToolbar` actually renders (`status.queueStatus`, `status.hasChapterAudio`, `status.liveSegmentProgressJob`, etc.), not the raw `chapterRender*SegmentIds` sets directly.
- **`useChapterStatus` itself is a pure derivation hook (no fetches)** — in isolation it could be called a second time with independently-resolved inputs. **Do not do this.** Its inputs (`generatingSegmentJob`, `activeBatch` derived from `scriptViewData?.render_batches`, `chapterRenderRenderingSegmentIds`/`chapterRenderPendingSegmentIds`) are themselves deep derivations inside `useStudioChapter` — depending on `scriptViewData` (a chapter-scoped fetch `useStudioChapter` owns), `chapterRenderActiveSegmentsMap` (backend map merged with a local fallback derived from `segmentProgress`), and `useSegmentHandoffQueue` (a stateful transition-smoothing hook — see the project's own "Progress debug workflow" memory on this handoff ring). Re-deriving a second, simplified version of these inputs from `AmbientStatus` would produce **a second, disconnected progress source that can silently disagree with Cast's own bar** — precisely the trap `01-map.md`'s Connections section calls out: *"Building K without J's state-lifting means inventing a second, disconnected progress source."*
- **`useStudioChapter` has real side effects** (multiple `useEffect`s, `api.*` calls for chapter/segment/analysis/script-view data). Calling the whole hook a second time (once from `AmbientStatus`, once from `CastToolBody`) would duplicate fetches and could race — this is the naive-but-wrong approach to rule out explicitly.
- **`DirectorsConsole` is already reachable from the data this needs**, so a real fix doesn't require large new plumbing: `BookLayout.tsx` mounts `DirectorsConsole` (line 280) inside `BookDataProvider` (wraps lines 327-365) — `useBookDataContext()` is already callable from `DirectorsConsole/index.tsx`'s own render scope. `BookLayout.tsx`'s `ChapterWorkspace` (lines 196-223) already syncs the route's `chapterId` into the `?chapter=` search param specifically so *"the DirectorsConsole tools (CastTool, BoothTool, etc... pick up the correct chapter"* — the same `useSearchParams().get('chapter')` resolution `CastToolBody` does is already available at the console-shell level without new routing work.
- **A second candidate mount point exists and matches "top bar" more literally**: `frontend/src/pages/Book/components/ChapterWorkspaceHeader.tsx` is, per `BoothTool/index.tsx`'s own comment (line 18), *"rendered once, above the whole console"* — the actual persistent page-level header for the chapter workspace (chapter title, prev/next nav, bookmarks). It currently takes only `bookId`/`chapters`/`activeChapterId` as props (no job/progress data). Either this component or `DirectorsConsole/index.tsx`'s own returned JSX satisfies "survives every mode switch" (neither remounts when `activeToolId` changes — only the tool body inside `DirectorsConsole`'s `tabpanel` div does). **RATIFIED by the owner, 2026-07-10: mount in `DirectorsConsole/index.tsx`**, per the map's own framing (part K names the console-shell level explicitly) — no longer an open choice, implement directly against this component.

## Target shape

1. **Extract the render-progress derivation out of `useStudioChapter.ts` into its own standalone hook** (e.g. `frontend/src/pages/Book/studio/useChapterRenderProgress.ts`), covering the slice from `chapterRenderActiveSegmentsMap` through `chapterRenderRenderingBatchProgressById` plus the `useChapterStatus(...)` call (`useStudioChapter.ts`'s current lines ~150-417 and 655-664) — parameterized by what's already resolvable without a second fetch (`chapterId`, `job`, `chapterJobs`, `segmentProgress`) plus whatever `scriptViewData` fetch it must now own (or continue to receive, if `scriptViewData` is lifted too — decide based on whether other Cast-only logic still needs the same fetch instance; if so, the fetch should live at whichever level is now shared, not be duplicated).
2. **`useStudioChapter` calls this new hook internally** and destructures its output instead of inlining the logic — this removes the duplication risk entirely: there is exactly one computation, `useStudioChapter` delegates to it, and it does not need to change its own public return shape (so `CastToolBody`'s existing destructuring keeps working unchanged — INV-5, no capability regression on Cast's own progress bar).
3. **Call the extracted hook once more at the console-shell level** (`DirectorsConsole/index.tsx`, resolving `chapterId`/`job`/`chapterJobs` the same way `CastToolBody` does via `useBookDataContext()` + `useSearchParams()`) and expose its output to a new `AmbientStatus` component — either by mounting `AmbientStatus` directly inside `DirectorsConsole/index.tsx` and passing the hook's output as props, or via a small context if `AmbientStatus` ends up mounted at `ChapterWorkspaceHeader`'s level instead (see the mount-point decision above). Whichever call site "owns" this second invocation, it is a **second live instance of the same derivation** (a second `scriptViewData` fetch, a second `useSegmentHandoffQueue` instance) — acceptable (two independent read-only subscriptions to the same server state, no shared mutable state to desync), but should not silently become a third or fourth call site elsewhere; keep it to exactly these two (Cast's, via `useStudioChapter`; the console-shell's, via `AmbientStatus`).
4. **Build `frontend/src/pages/ChapterEditor/components/AmbientStatus/`** — a small pill component rendering Idle/Queued/Preparing/Rendering `N%`/Finalizing/Done/Error off the extracted hook's `status.queueStatus` (+ progress value from `chapterRenderRenderingBatchProgressById` or `status.liveSegmentProgressValue`, whichever the extracted hook exposes), matching the state names `ChapterScriptToolbar` already renders inside Cast — this is a relocation of an existing state machine's *display*, not a new one.
5. **Click-to-open popover** (§4: "Click for a non-modal segment-level popover"): in scope per the design doc, but may ship as a minimal v1 (a small list of segment ids + phase, no polish) consistent with how this doc elsewhere marks features "ships v1 as model + display" — do not silently drop it, but don't over-invest in it either.
6. **Mount `<AmbientStatus />`** at the decided location (see above) so it renders regardless of which Director's Console tool is active.
