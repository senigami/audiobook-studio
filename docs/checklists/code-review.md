## Boundary & State-Combination Coverage

- [ ] For any component with more than one branching dimension (e.g. a count-tier AND a status enum), test the COMBINATION at each branch boundary, not each dimension independently. <!-- added 2026-07-04, source: self-caught (fusion review) — SegmentRenderMonitor's >60-segment summary view had zero failure indicator; the >60 test used only done/preparing segments, the failed-segment test used only <=60 segments, so the one combination that mattered was never exercised -->
- [ ] When a dispatch function offers more than one routing branch (e.g. a legacy per-engine/per-kind registry handler vs. a new task-shape-aware path) and the choice depends on a per-engine registration table, test the NEW path against EVERY engine that has an entry in that table — not just whichever engine happens to have no legacy registration. An engine's absence from the table makes the new path pass "by accident" (nothing else could have run), which is exactly the condition that hides a routing-precedence bug for every other registered engine. <!-- added 2026-07-05, source: user-flagged via Fable adversarial review — W-PAR 008's synthetic-fan-out-child bridge routing was validated only against `mixed` (whose manifest has `worker_logic: null`); xtts and voxtral both still have legacy `engine_handlers` registrations that silently pre-empt the intended bridge path in `_dispatch_segment`'s registry-first lookup order (app/orchestration/scheduler/orchestrator_helpers.py:1518-1523) -->
- [ ] When a function has a "source larger than target" main path and a "source smaller than target" edge path (resize/downsample/pagination logic), write a fixture that hits the smaller-than-target case explicitly — don't assume the main-path fixture also covers it. <!-- added 2026-07-04, source: self-caught (fusion review) — usePeaks's downsample only had fixtures >= PEAKS_COUNT samples, so a padding bug that flatlined the tail of any shorter clip shipped untested -->
- [ ] When changing a threshold/boundary constant, grep existing tests for hardcoded values near the OLD boundary — they may silently start exercising a different code path than the one they were written to test, while still passing. <!-- added 2026-07-04, source: self-caught (final sign-off review) — two PlayerBar transport-control tests used duration=120 (the old DURATION_BOOTSTRAP value); when the constant changed to 30 they silently switched from the waveform path to the plain-bar path with no assertion noticing -->

## Reused Utilities at New Call Sites

- [ ] Before calling an existing shared utility from a new call site, enumerate its edge-case branches (empty/undefined/null inputs especially) and confirm each one is still the RIGHT behavior for the new caller — don't assume behavior tuned for existing callers transfers. <!-- added 2026-07-04, source: self-caught (fusion review) — getDefaultVoiceProfileName's engines=[] fallthrough was fine for display-only callers but let the new AI-casting caller silently assign a voice with unchecked engine readiness -->

## Spec/Doc-Value Provenance

- [ ] A code or test comment claiming a value is "per spec" or "spec-defined" must be checked against the literal spec text at the time it's written, not copied from an earlier draft or assumption. <!-- added 2026-07-04, source: self-caught (fusion review) — DURATION_BOOTSTRAP was 120 (4x the spec's ~30s), and the test file's own comment falsely asserted the value was spec-verified -->
- [ ] When a consolidation/refactor "upgrades" one code path's behavior to match another's (or to match what a binding spec already claims), treat it as a behavior change: find the matching spec SECTION (not just the obviously-named spec file) and land a spec_version bump + changelog row in the same change. A spec whose text already describes the NEW behavior is evidence of pre-existing spec/code drift being resolved — record the realignment (per the resolve-drift-explicitly rule), don't conclude "no spec work needed". Then re-check every OTHER code path the same spec sentence names: if any still has the old behavior, the sentence is now half-true — scope the claim and flag the residual drift explicitly. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — PL-2 upgraded xtts/voxtral bake's _group_needs_render from bare exists() to validated-artifact metadata; queue-jobs.md §3.7 already claimed "never raw file existence alone" (written drifted in the 1.4.0 reconcile), the implementing agent checked only plugin-contract.md and reported spec work as "a no-op", and §3.7's co-named _group_is_done (xtts standard path) remained a bare exists() check with the spec sentence silently covering for it -->

## Suppressing or Gating a Shared Chokepoint

- [ ] Before adding an early-return / suppression flag to a publish, broadcast, logging, or event chokepoint, enumerate EVERY signal multiplexed through that chokepoint and confirm each one is individually safe to drop — a chokepoint added for one channel (e.g. durable job rows) usually carries co-tenant channels (e.g. segment-scoped frames) whose consumers key on different ids and never cared about the channel being fixed. Trace each downstream consumer to its actual key, don't reason from the id that motivated the suppression. <!-- added 2026-07-04, source: self-caught (review-ratchet pass) — the W-PAR ephemeral early-return in orchestrator _publish correctly killed phantom job rows but also killed segments.progress frames flowing through the same call; the frontend keys the live per-segment bar by segmentId, so the phantom jobId was never load-bearing for those frames and they had to keep flowing -->
- [ ] A helper function shipped "for future call sites" with zero current callers must still land with a direct unit test in the same change — untested-and-uncalled code is unverified in every branch, including trivial ones like result-row column aliasing. Prefer wiring at least one real caller or deleting it. <!-- added 2026-07-04, source: self-caught (review-ratchet pass) — chapter_completion_by_size landed advertised in two specs and the changelog with no caller and no test; its sqlite3.Row["total_chars"] aliasing had never executed -->

## Porting Code From a Mock/Reference Implementation

- [ ] When porting an interactive control from a mock/reference implementation, diff EVERY interactive handler's target/effect against the current task's own acceptance criteria — not just against the mock. A change made elsewhere in the port (e.g. reordering a constants array) can leave a copied handler LOOKING correct while its behavior (jump-to-extreme vs. step-by-one) now contradicts what the task doc actually asks for. Add a test exercising every ported interactive element (button/gesture/key) — zero test coverage on a ported control is exactly where this survives to ship. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — WaveformTapeZoom's ±buttons were ported verbatim from MockTapeControls' jump-to-extreme `onClick`s, but task 007's acceptance criteria explicitly says the buttons must "step" the index; zero tests exercised them so it shipped uncaught -->

## React/Browser Event API Semantics

- [ ] A handler calling `e.preventDefault()` on a `wheel`, `touchstart`, or `touchmove` event bound via a React JSX prop (`onWheel`, `onTouchStart`, etc.) must instead use a native `element.addEventListener(type, handler, { passive: false })` — React registers these event types as passive at the document root (React 17+), so `preventDefault()` inside the synthetic handler is a silent no-op in real browsers. jsdom's `fireEvent` does NOT reproduce this restriction, so a behavioral unit test will pass either way — verify with a structural test (spy on `addEventListener` and assert the `{ passive: false }` options object), not a behavioral one. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — WaveformTape's wheel-zoom handler used React's onWheel + e.preventDefault(), which snapped the zoom but did not stop the page from scrolling in a real browser -->

## JSX Text vs. String-Literal Escapes

- [ ] A `\uXXXX` (or other backslash) escape sequence placed as BARE JSX text — i.e. outside any `{...}` expression or quoted string — renders literally to the user; it is not a JS string literal and JSX does not parse backslash escapes in text children (it only decodes HTML entities like `&hellip;`/`&nbsp;`). Any special character needed in JSX text must be typed as a real UTF-8 character, an HTML entity, or wrapped in a JS string/expression (`{'—'}` or a template literal inside `{...}`) so the escape is actually evaluated. Grep the diff for `\\u` sequences and check each is inside quotes/braces, not sitting directly in element children. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — App.tsx's startup-error banner wrote `{initialError} — retrying automatically&hellip;` as bare JSX text; the `—` rendered as the literal six-character string, while the adjacent `&hellip;` correctly decoded, making the bug easy to miss on a quick read -->

## Test Isolation from Background Timers/Polling

- [ ] When a test asserts that a MANUAL control (a button, a user action) produces some end state, and the component under test also has a BACKGROUND timer/poll/retry loop that could independently reach that same end state, the test must isolate the manual path from the background one (e.g. fake timers advanced only up to just short of the background loop's interval) — not just trigger the action and `waitFor()` the end state with a timeout wide enough for the background loop to also fire. Verify by mutating the control's handler to a no-op and confirming the test now fails; if it still passes, the assertion is proving the background loop works, not the control. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — App.test.tsx's "Retry now" button test used a 2000ms real-timer waitFor while the hook's own 1000ms auto-poll was still running underneath; neutering the button's onClick left the test passing because the auto-poll's second fetch cleared the error banner on its own -->

## HTTP Response Handling

- [ ] A raw `fetch()` call that bypasses the app's shared response-parsing chokepoint (`parseApiResponse` in `frontend/src/api/index.ts`, which checks `res.ok` before trusting the body — see F5) must still check `res.ok` itself before calling `res.json()`. An HTTP error status with a valid JSON or HTML body does not reject the fetch promise — it resolves normally, so skipping the `ok` check silently treats a 500's error payload (or an HTML error page, surfacing as a cryptic "Unexpected token '<'") as valid application data. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — useInitialData.ts's fetchHome does its own raw fetch (for a `cache: 'no-store'` option parseApiResponse's callers don't need) and had no res.ok check; the F15 fix added error handling for network rejections but initially left this HTTP-error path silently mis-parsed -->

## Accessibility of Dynamic UI States

- [ ] A newly introduced error/failure banner, toast, or alert region must carry `role="alert"` (or `aria-live="assertive"`/`"polite"` as appropriate) so assistive tech announces it when it appears — a purely visual differentiator (an icon, a border color) is invisible to screen reader users, even when there's also distinguishing text for sighted users. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — F15's startup-error banner had visually distinct copy and a colored indicator but no aria-live/role="alert", so it was silent to screen readers -->

## Writing Your Own Static Enforcement Checks

- [ ] When writing a static import-boundary or banned-pattern checker (regex or AST-based) for a pytest guard, test it against the MOST IDIOMATIC form of the violation it exists to catch, not just the obvious one. For Python import boundaries specifically: both `import pkg.sub.mod` and `from pkg.sub import mod` must resolve to the same dotted path before being checked against forbidden prefixes — a line-regex that only captures the `from`-clause's module token will silently let `from app.jobs import worker` through a check aimed at `app.jobs.worker`. Prefer `ast.parse`/`ast.walk` over line regex for this class of checker; it handles multi-line and aliased imports for free. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — BE-2's new tests/orchestration/test_import_boundaries.py used a from-or-import regex that only recorded the from-clause module, missing exactly the submodule-import form its own forbidden-prefix list (app.jobs.worker, app.db.queue) was written to catch -->

## Fixing a Test's Patch Target

- [ ] When "fixing" a test by retargeting a `monkeypatch`/patch call to a different attribute path, trace what the NEW target actually affects at runtime (read the function that consumes it, don't assume the name implies the wiring) before declaring it fixed — a passing suite proves nothing if the new target is ALSO a dead alias the real code path never reads. Check whether the module you're patching has its own `X = other_module.X`-style alias one level removed from the thing that's actually read. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — BE-1a retargeted a test's patch from app.api.web.REPORT_DIR to app.api.routers.analysis.REPORT_DIR, but analysis.py's own REPORT_DIR was itself a dead self-alias (get_report_dir() reads config.REPORT_DIR directly); the test only ever passed via a third, separate patch of app.core.config.REPORT_DIR that was already present -->

## Aggregation Sampled at the Wrong Event Boundary

- [ ] When a periodic/aggregate snapshot (e.g. "what's currently active") is only computed at ONE lifecycle event (e.g. only on completion), check whether that boundary is structurally incompatible with the state the snapshot needs to observe — the thing being sampled may ALWAYS have just changed at exactly that instant (the item that triggered the sample is now excluded, and whatever comes next hasn't started). Verify by asking "at the exact moment this runs, could the interesting case ever actually be true?" — not just "does the aggregation logic look correct in isolation." A completion-only sample of "what's in-flight" is empty by construction, regardless of concurrency level, and unit tests that construct the snapshot directly (bypassing the real call site) won't catch it. <!-- added 2026-07-05, source: fusion-design-panel diagnosis + Fable plan review — ChapterSynthesisTask._current_active_segments_map was only ever invoked from _publish_progress inside the as_completed loop (segment_synthesis.py), i.e. only at group-COMPLETION boundaries; the just-finished child was already excluded (finished=True) and the next hadn't started, so the map was always empty at cap=1 AND at genuine concurrency — no segment ever visibly highlighted or animated. Fix: sample from an event-driven, continuously-updated source (each child's own already-rate-limited progress tick) instead of re-deriving state only at the one boundary where the answer is guaranteed to be "nothing." -->

## Wire Contract Fields Added to One Frame Type But Not Its Siblings

- [ ] When adding a new field to a wire event's payload builder, grep for EVERY OTHER builder that emits a semantically similar frame (e.g. a per-job status frame vs. a per-chapter progress frame vs. a per-segment frame) and add the same field to each one that could plausibly need it — not just the first one you touched. A field usable data can be written correctly to backend state forever and still never reach the client if the ONE frame type that would carry it during the relevant window (e.g. a mid-render, status-unchanged tick) has no parameter for it, while a DIFFERENT frame type (e.g. one only sent on status transitions) happens to support it. <!-- added 2026-07-05, source: fusion-design-panel diagnosis + Fable plan review — build_queue_item_status_event (app/api/contracts/events.py) already had an active_segments_map parameter; build_chapter_progress_event did not. queue.items only fires on a status change or terminal reset, so a mid-render map update (no status change) had no frame at all that could carry it — the backend could write a perfectly correct map to job state on every tick and it would never once reach the frontend. -->

## Declared-but-Unused Props/Parameters

- [ ] When a function/component/hook accepts a parameter in its type signature, grep the function BODY (not just the signature) to confirm it's actually destructured and read somewhere — a parameter that's threaded all the way through the call chain (parent components explicitly passing it down) but never consumed at the final destination is a strong signal that a feature was half-wired and silently abandoned, not that the data is unneeded. Treat "prop exists in the interface, wired by every caller, unused in the body" as a defect to investigate, not a harmless unused import. <!-- added 2026-07-05, source: fusion-design-panel diagnosis (Skeptic persona) — useStudioChapter.ts accepted `segmentProgress?: Record<string, SegmentProgress>` and it was threaded correctly from useJobs.ts through BookLayout/BookDataContext/StudioStage, but never destructured or referenced anywhere in the hook body — real live per-segment data was flowing all the way to the door and being discarded there. -->

## New Duck-Typed `getattr(task, flag, False)` Checks vs. Bare `MagicMock()` Fixtures

- [ ] When adding a new `getattr(obj, "new_flag", False)`-style duck-typed check to a widely-shared function, grep the test suite for every bare `MagicMock()`-based fixture that flows through that function and add `fixture.new_flag = False` explicitly, mirroring how the function's EXISTING duck-typed flags are already explicitly set on those same fixtures. An unconfigured attribute access on a bare `MagicMock()` auto-vivifies a new truthy child mock rather than raising `AttributeError` — so `getattr(mock, "new_flag", False)` silently returns a truthy mock instead of the intended `False` default, inverting the check for every test that predates the new flag. Run the FULL test suite (not just the directories you touched) before considering a shared-chokepoint change complete — this class of regression lives in test files the "obviously relevant" directory list won't include. <!-- added 2026-07-05, source: self-caught (full-suite run before commit) — added `skip_registry_dispatch` to `_dispatch_segment`'s existing `getattr(task, "is_chapter_fanout", False)`-style checks; three tests in tests/engines/test_xtts_timing.py used bare `MagicMock()` tasks that already explicitly set `is_chapter_fanout = False` (with a comment noting exactly this Mock gotcha) but had no reason to know about the new flag, so they silently started skipping the registry handler they were written to exercise and crashed reaching an unconfigured `self.voice_bridge` -->

## Pre-flight Validation Before Network/Process Boundaries

- [ ] A function that assembles a request/payload from caller-supplied or re-derived data (text, a script list, a batch) before calling an external process/network boundary (an HTTP client, a subprocess, an engine bridge) must short-circuit BEFORE the call when the assembled payload legitimately resolves to "nothing to send" — treat an empty result as a benign no-op (skip the call, succeed) rather than dispatching it and relying on the remote side's validation error. The tell: a request-building function whose only non-empty check happens server-side (a 422/400 from the callee), with no local `if not payload: return` before the network hop on the caller's side. Relying on the server's rejection turns a benign "already satisfied, nothing left to do" condition into a hard job failure with a confusing error message. <!-- added 2026-07-05, source: user-flagged via Fable adversarial review — handle_xtts_standard's chapter-loop can legitimately end with zero groups needing render (a sibling fan-out child already rendered everything); it unconditionally called generate_via_bridge(text="", script=[], ...) anyway, which propagated through app/jobs/handlers/bridge_helpers.py's own equally-unguarded generate_via_bridge all the way to the TTS server's "text must not be empty" 422 -->

## Extraction Reordering Resource Lifecycles

- [ ] When extracting inline logic into a shared helper, diff the ORDER of side-effecting operations (resource acquisition — temp files, locks, staged directories — vs. fallible operations) between the pre- and post-extraction code, not just the logic itself. Moving a fallible step (e.g. staging/validation) from before a resource-creating step to after it (or vice versa, e.g. by relocating it inside the new helper) can turn a previously-safe failure path into a leak, even when every individual formula/branch is preserved correctly. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review — extracting Voxtral's _run_voxtral_generate moved reference-audio staging (which can raise) to happen AFTER the caller's mp3 temp-wav mkstemp, inverting the original order where staging failed before the temp file existed; a staging failure now leaks an empty temp .wav the pre-extraction code never created in that path -->

## Flipping a Default/Cap Setting Without Its Paired Enable Gate

- [ ] When raising a cap/limit/threshold setting (e.g. a concurrency cap, a rate limit, a batch size) that is supposed to make a previously-inert code path actually active, grep for a SEPARATE boolean/env-gated flag that independently controls whether that path is even reachable at all — a "ships dark" feature often has two knobs (a HOW-MANY setting and a WHETHER-AT-ALL gate) added at different times by different tasks, and raising the first without checking for the second silently changes nothing observable while looking, on inspection, like the feature is now live. The tell: a cap/limit constant whose default changed in a changelog entry, with no changelog entry anywhere flipping a same-area boolean env/feature flag in the same or an adjacent commit. <!-- added 2026-07-06, source: user-flagged (owner reported the "parallel by default" fix had no effect) — `92bbb443` raised `tts_parallel_cap`'s default 1->2, but `app/orchestration/scheduler/resources.py`'s `_engine_class_admission_enabled()` (env-gated via `ENGINE_CLASS_ADMISSION`, a SEPARATE "ships dark" flag from W-PAR task 001, meant to flip in task 007 but never did) still defaulted OFF, so every synthesis claim kept routing through the legacy single-flight exclusive gate and renders stayed genuinely sequential regardless of the cap. Cost a full owner-reported debugging round to find; also flagged as a docs/lessons/ project lesson the same day. -->

## Reusing a Marker/Log-Parsing State Machine Under Concurrency It Was Never Tested Against

- [ ] Before merging a change that enables real concurrent execution of a previously-sequential-only marker-parsing or event-dispatch state machine (log line parsing, a sticky "currently active X" variable derived from a stream of untagged/partially-tagged events), write a test that runs TWO instances concurrently through the SAME shared underlying stream/dispatcher and asserts no cross-instance state leak — not just that two instances run in parallel without crashing/deadlocking. A permit-by-default filter (accepts any event whose identifying tag doesn't EXPLICITLY mismatch, rather than requiring an explicit match) is invisible at cap=1 and only manifests once two real concurrent producers can both feed the same consumer. <!-- added 2026-07-06, source: self-caught + Fable adversarial review — app/orchestration/scheduler/orchestrator_helpers.py's `_dispatch_segment` log_listener (a marker-parsing state machine originally built for one sequential dispatch) was reused per fan-out child once `ENGINE_CLASS_ADMISSION` defaulted on; a sticky `active_seg_id` combined with a permit-by-default `if line_task_id and line_task_id != context.task_id: return` filter meant a single foreign-sid marker line (arriving via an unrelated unsynchronized-stderr-write race between two concurrent children) poisoned every subsequent same-task PROGRESS tick until the next real START_SEGMENT. The only pre-existing test exercising 2 concurrent fan-out children used `engine_id="mixed"`, which bypasses this exact state machine (`render_one_group`'s local-execution path) — so the untested variant looked covered. -->

## Known Recurring Violation Patterns

- **`\uXXXX` escapes typed as bare JSX text instead of inside a string/expression** — copy containing a special character (em dash, ellipsis, curly quote) gets written directly as JSX element children with a backslash escape, which JSX passes through as literal text since it isn't a JS string literal — while an adjacent HTML entity in the same text node (`&hellip;`, `&nbsp;`) DOES correctly decode, making a quick visual scan of the diff misleadingly reassuring. The tell: a `\u` sequence sitting in JSX children with no enclosing quotes or `{}`. Fix pattern: put the character inside a JS string/template literal within `{...}`, or type the real UTF-8 character, or use the entity form — then assert the exact rendered text (not a substring match) in a test, since a substring match can still pass against the broken literal-escape output. <!-- added 2026-07-04, source: user-flagged via Fable adversarial review -->
- **Fix-one-channel, kill-the-bus suppression** — a bug about ONE kind of output flowing through a shared emit path gets fixed by suppressing the WHOLE path for the offending source, silently dropping the other kinds of output multiplexed through it. The tell: a new `if <flag>: return` (or equivalent gate) placed above a function that emits to more than one topic/table/stream, justified by a comment that mentions only one of them. Fix pattern: push the flag INTO the emitter and suppress per-channel, keeping the channels whose consumers are keyed independently of the motivating bug; pin with a test asserting both "banned channel silent" AND "surviving channel still emits". <!-- added 2026-07-04, source: self-caught (review-ratchet pass, W-PAR ephemeral publish) -->


- **Plausible-but-unverified "spec-defined" claims** — a value gets carried forward (from an earlier draft, a different task, or plain assumption) with a comment asserting it matches the spec, and nobody re-opens the spec to check. The tell: a numeric/threshold constant with a comment citing a spec section but no direct quote of the spec's actual wording next to it. Fix pattern: require the comment to include the literal spec phrase, not just a section reference.
- **Draft plan docs speculating about an unbuilt dependency's interface** — a task file written before its dependency shipped assumes props/exports that never end up matching the real thing once built. The tell: a "Target shape" or "Contract" section in a task doc referencing a component/prop name that doesn't appear anywhere in the actual codebase yet. Fix pattern: flag such sections as speculative in the doc itself, and re-derive from the real shipped interface before executing the dependent task (see the stale-draft warning pattern added to design-docs/plans/active/audio_player_waveform_scrubber/tasks/008-*.md). **Recurred 2026-07-04** (Fable adversarial review): task 009's pre-drafted CSS assumed a `.tape-zoom-btn` class and a live "Library" cover-slider to reuse `ns-size-*` classes from — neither matches reality (the shipped component renders `ns-size-glyph tape-zoom-glyph-hit`, and `ns-size-*` only exists in the demo mock's `mockup.css`, not the live bundle). Corrected in-place in both 007 and 009's task docs rather than left to surprise whoever executes 009.
- **Ported interactive control not re-validated against the current task's contract** — porting an interactive element (button/gesture/key handler) verbatim from a mock/prototype while ALSO changing something structural in the port (e.g. reversing a constants array's order) can leave the copied handler passing a superficial glance while contradicting the current task's own acceptance criteria. The tell: a ported handler with zero direct test coverage, especially one using a "jump to extreme" idiom carried over from a differently-ordered source array. Fix pattern: whenever a port also changes an underlying ordering/constant the ported handler depends on, re-derive (don't copy) every handler that referenced it, and add a test per ported interactive element before considering the port complete.
- **A confident verification claim in a commit message isn't independently re-derived** — "verbatim," "no-op," "byte-identical," "none of these distinctions were merged away" are claims the author believed after their own check, but self-verification shares the author's blind spot by construction. The tell: a commit message asserts equivalence/safety in strong language with no independent re-derivation attached. Recurred twice in one day across otherwise-clean, well-verified batches: a "fixed" monkeypatch target that was itself still dead one level down, and a "clean extraction" that quietly reordered a resource-acquisition step relative to a fallible one. Fix pattern: an adversarial reviewer (human or Fable-tier model) re-deriving the specific claim from a pre-image diff or from first principles — not re-reading the stated reasoning and nodding — is what catches this; budget for it even on "mechanical, low-risk" cleanup passes.
- **A shared utility/handler built for one call site's assumptions gets reused unmodified at a new call site with a different concurrency/scoping model** — the utility's edge-case behavior (an empty/default fallthrough, or a "recompute everything from live shared state" assumption) was safe under the ORIGINAL caller's single-invocation-per-unit-of-work contract, but the new caller invokes it multiple times per unit (once per fan-out child, once per UI action) without re-deriving whether that assumption still holds. The tell: a new call site invoking an existing function/handler with no new isolation/scoping parameter, where the function internally re-queries "what needs doing" from a shared store rather than being handed its own explicit slice. Fix pattern: before wiring a new (especially concurrent/fan-out) call site onto an existing handler, trace whether the handler treats its unit of work as SELF-CONTAINED (parameterized) or RE-DERIVED (queries shared state); a re-deriving handler must either be re-scoped to accept an explicit boundary, or a fan-out-aware isolation layer must intercept before it — never fan out N callers onto it unmodified. **Recurred 2026-07-05** (fusion-panel diagnosis, Fable adversarial-verified): W-PAR's chapter-fanout children were meant to route through `_SyntheticSegmentTask.to_bridge_request()` (an isolated, one-group-per-child path, per the class's own "W-PAR 008 R1" owner ruling), but `_dispatch_segment`'s pre-existing registry-based dispatch (`app/orchestration/scheduler/orchestrator_helpers.py:1518-1523`, matching on engine name alone) runs FIRST and silently wins for every engine with a legacy registered handler (xtts AND voxtral — only the `mixed` engine's manifest happened to have no registration, which is why W-PAR 008's own testing never caught it). Every fanned-out child then executed the legacy whole-chapter handler (`handle_xtts_standard`), which re-derives ALL of the chapter's remaining groups from a live DB query on every call with no per-child scoping — so the first-dispatched child silently rendered every other child's work too, and every subsequent child crashed with an empty-payload 422 once nothing was left to render. (First occurrence: `getDefaultVoiceProfileName`'s `engines=[]` fallthrough above.) **Recurred again 2026-07-06** (self-caught + Fable adversarial review, same incident as the marker-parsing entries above): `orchestrator_helpers.py`'s log_listener marker state machine (built and tested only for cap=1 sequential dispatch) was silently reused per concurrent fan-out child once `ENGINE_CLASS_ADMISSION` finally defaulted on — its per-call closure state WAS correctly isolated (verified exhaustively by direct code reading), but the shared PROCESS-LEVEL stderr stream it reads from was not, and the one existing "concurrent fan-out" test exercised a call path (`engine_id="mixed"`) that never touches this state machine at all, so the untested variant looked covered by an adjacent test. Third occurrence in two months on the same subsystem (W-PAR fan-out) — this is now a standing risk area, not a one-off: any future change to `_dispatch_segment`/fan-out routing needs a concurrency test that exercises the ACTUAL production engine path (xtts/voxtral), not only `mixed`.
- **`preventDefault()` inside a passive-by-default React synthetic handler** — `onWheel`/`onTouchStart`/`onTouchMove` are registered passive at the document root by React 17+, so calling `e.preventDefault()` inside them is a silent no-op in real browsers, even though jsdom-based tests can't detect the difference and will pass either way. The tell: `e.preventDefault()` inside a React JSX wheel/touch prop handler with no corresponding native `addEventListener` call anywhere nearby. Fix pattern: attach a native listener via ref/`useEffect` with `{ passive: false }` instead, and test it structurally (assert the `addEventListener` call's options), not behaviorally.
- **Unsynchronized writes to a shared process stream from concurrently-running request handlers** — a long-lived server process handles N concurrent requests on a thread pool (FastAPI/Starlette `run_in_threadpool`, or equivalent); more than one code path relays lines to that process's own shared `sys.stdout`/`sys.stderr` for an external reader (a log-tailing watchdog) to parse, and each path writes via a bare `print(..., file=sys.stderr)` or `sys.stderr.write(...)` with no lock. `print()`/`write()` are not single-syscall-atomic across the content and the trailing newline, so two threads' writes can interleave into one corrupted/merged physical line. The tell: more than one function in the same process writes to the shared stream the external reader parses, and grepping for the writer's own locking primitive turns up nothing, or turns up MULTIPLE separate lock objects (a lock per writer does not serialize the writers against each other — they must share one instance). Fix pattern: centralize ALL such writes through one function backed by one process-wide lock in a shared leaf module every writer imports, writing the fully-composed line (content + newline) in a single locked `write()` call. **Recurred within the same incident** (2026-07-06): the fix initially added the lock only to `plugins/tts_xtts/plugin/server/engine.py`'s marker-relay writer; running the resulting checked invariant's grep against the wider server-context codebase immediately surfaced a SECOND, independent unlocked writer (`plugins/tts_xtts/plugin/core/diagnostics.py#emit_diagnostics`, called from `implementation.py`'s `xtts_generate`/`xtts_generate_script` on the same per-request threadpool threads) that would have reintroduced the identical race from a different call site. Moved the lock to the shared leaf module (`diagnostics.py`) and had `engine.py` import it, rather than each module defining its own — a per-writer lock would not have closed the race.
