# Security Review Checklist
<!-- Maintained by review-ratchet. Every check exists because something escaped once. -->
<!-- Seeded 2026-07-04 from the HuggingFace integration's security audit (fusion-reasoning panel). -->

## Independent Enforcement of Security Properties

- [ ] When a security-relevant guarantee (path containment, filename sanitization, size limits) currently holds only because of a third-party dependency's internal behavior, add an explicit, independent check in this repo's own code. A dependency's undocumented internal safety is not a contract we control and can change across versions without notice. <!-- added 2026-07-04, source: self-caught (fusion security audit) — HFHubClient.download_files was safe from path-traversal filenames only because the installed huggingface_hub version happened to sanitize them; requirements.txt pins an unpinned >=0.20 lower bound -->
- [ ] Before writing an attacker/remote-source-controlled string to a file path, check it against BOTH a basename-only helper (safe_basename) AND an explicit check for `..` anywhere in the full path's segments — a basename-only check alone loses traversal context embedded earlier in the path (e.g. `audio/../../../etc/passwd.wav` still has a valid-looking basename). <!-- added 2026-07-04, source: self-caught (fusion security audit + final sign-off) -->

## Resource Exhaustion Before Expensive Operations

- [ ] Before downloading/processing a remote-source-controlled list of files, apply an extension/type allowlist AND a count cap BEFORE any download call, not after. Verify (don't just assume) that the cap is applied to the FILTERED list, not the raw list — capping before filtering can produce zero usable results even when a legitimate item exists further down the raw list. <!-- added 2026-07-04, source: self-caught (fusion security audit) — HF download_files now filters extensions then caps at MAX_DOWNLOAD_FILES=20, verified in that order by the final sign-off -->
- [ ] When adding or reusing an upload/import extension allowlist, verify each allowed extension against the actual parser path that will consume it — UI `accept` text and historical labels are not proof of support. A file type that passes the allowlist but is decoded by a plain-text parser fails silently instead of producing the expected unsupported-file error. <!-- added 2026-07-08, source: adversarial review — chapter import allowed `.docx`/`.epub`, but the backend upload path reads bytes and decodes them as UTF-8 text with replacement rather than parsing those formats -->
- [ ] For any new outbound network call added in this session, check whether the app's threat model assumption (e.g. "localhost-only, no LAN exposure") is actually still true at the exact point the new code executes — cite the concrete evidence (e.g. the launcher's bind address), don't just restate the assumption. <!-- added 2026-07-04, source: self-caught (fusion devil's-advocate review) — verified run.sh has no --host flag and binds uvicorn's 127.0.0.1 default before treating a missing timeout/size-cap as merely a hardening nice-to-have rather than a blocker -->

## Known Recurring Violation Patterns

- **Security property borrowed from a dependency, not owned** — a new integration with a third-party library relies on that library's internal validation/sanitization for a property this app actually needs guaranteed (path safety, input bounds), without adding its own check. The tell: a security-relevant code path that has no repo-native validation call (e.g. no `safe_basename`/`contained_path`) even though attacker/remote-controlled data reaches a file write or shell-adjacent operation. Fix pattern: this repo already has `app/utils/pathing.py` helpers — every new file-writing path fed by external data must call one of them explicitly, regardless of what the upstream library already does.
