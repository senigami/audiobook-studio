## Before Trusting a Status Marker

- [ ] Before starting work "blocked on" or "gated by" another task's checkbox in TASKS.md (or any status marker), verify the gating task's ACTUAL status via `git blame`/`git log -- <file>` or a direct grep of the referenced code — don't trust the checkbox alone. <!-- added 2026-07-04, source: self-caught, recurred 3x in one session (W-PAR 006 marked incomplete but shipped in fa6cf37b; the WL1 gate on the chapter-editor art-program was marked open but all 4 bugs were already resolved; the "AI casting + voice metadata UI" section was marked undone but was already shipped live in commit 1e475d5e) -->
- [ ] When a plan/phase doc explicitly forbids building something ("do NOT build X", "NO X integration") and you're asked to build X anyway, read that doc's stated REASON for the prohibition before proceeding — if the reason was sequencing/scope (not a substantive legal/security/product objection), it's safe to supersede with an explicit note; if the reason was substantive, escalate to the user instead of silently building past it. <!-- added 2026-07-04, source: self-caught (fusion devil's-advocate review) — R5-T4's "do NOT build HF" turned out to be phase-sequencing (that phase was UI-only, no app/ changes allowed), not a legal/licensing/abuse-vector objection; confirmed by reading one level up in 01_overview_and_phases.md before proceeding -->

- [ ] When a plan/map doc claims an existing helper "already produces" a required output shape (justifying reuse over reimplementation), verify each CONDITIONAL branch of that helper against the data the new call site will actually feed it — grep for who writes the fields the helper keys on, and confirm they're populated on the new caller's real inputs, not just in test fixtures. A helper that emits the load-bearing piece only inside an `if manifest.get(X):` branch "already produces" nothing for callers whose X is never written. <!-- added 2026-07-04, source: user-flagged via Fable accuracy review — the huggingface_voice_upload plan asserted bundles.generate_readme_md "already produces exactly" the HF repo-spec §7 shape, but its widget block (the plan's own success criterion 1) is gated on voice_manifest["samples"], which only the v1 migration ever writes and which current voices lack; every test the plan specified used fixtures that hand-wrote samples[], so the gap would have shipped silently -->

- [ ] When a spec changelog row advertises a new helper/field/capability "for" some consumer, state explicitly whether any consumer is wired YET — an unqualified "for resume/recompute call sites" reads as live wiring to a future reader; follow the computed-but-not-wired convention (live-events.md 1.9.3) when it isn't. <!-- added 2026-07-04, source: self-caught (review-ratchet pass) — queue-jobs.md 1.11.0 advertised chapter_completion_by_size for resume/recompute call sites while it had zero callers -->

- [ ] A plan/doc claim that a LIST of symbols has "no test coverage at all" is a conjunction — verify it per symbol, with a separate grep for EACH named function (and for its API-route/hook callers, since coverage often lives at the caller layer under a different name), before writing it down; don't grep the rarest symbol and generalize to the whole list. <!-- added 2026-07-04, source: user-flagged via Fable accuracy review — span_word_boundary_snapping task 002 claimed `_apply_range_assignment`/`save_script_assignments` had zero coverage; the range path genuinely had none, but save_script_assignments was directly exercised by tests/db/test_segment_voice_invalidation.py and the range-payload hook by frontend/tests/unit/hooks/useChapterAssignments.test.tsx — a follow-up owner would have re-planned already-covered work -->

- [ ] Before a research/proposal doc RECOMMENDS adding a field/block/mechanism (or poses an "should X adopt Y?" open question), grep the shipped schemas AND generators for that exact mechanism first — a versioned schema that already *requires* the field, or an export path that already emits the pattern, turns the recommendation from "add" into "populate/consume", and shipping the wrong verb sends a future implementer to re-build existing contract surface. <!-- added 2026-07-04, source: Fable accuracy review — research_voice_engine_marketplace_ui_prior_art.md recommended "adding a declarative preview-sample block" and asked whether voice bundles should "adopt" the HF widget shape, while voice.schema.json already REQUIRED samples[]={path,text,primary} and bundles.py generate_readme_md already emitted the HF widget output.url fallback; only the engine manifest/registry side actually lacked it -->

- [ ] When summarizing what a plan/doc "already ships", keep built items (grep-verified in code) and specified-only items (schema sketched in the doc, implementation checkboxes unchecked) in separate clauses — a specified-only item listed alongside "a working <Component>" inherits the built claim by adjacency. Verify each item in the list independently against the codebase. <!-- added 2026-07-04, source: Fable accuracy review — the same research doc's "doc 05 already ships" list put the manifest.json `distribution` block (specified in §1.2, steps X5/2.5/3.5 unchecked, no in-tree manifest carries it, loader ignores it) between two genuinely-shipped items (the registry catalog+route and OfficialRegistryPanel.tsx) -->

## Known Recurring Violation Patterns

- **Stale completion checkbox, current code** — work actually ships (often bundled into a differently-named commit) but the tracking doc's checkbox for that specific line item never gets flipped, so a later session either re-does already-done work or incorrectly treats something as blocked. The tell: a checkbox says `[ ]` but grepping the referenced file/function in the actual codebase finds it fully implemented and tested. This is the *inverse* of normal doc rot (docs usually overclaim; this repo's failure mode is the opposite — code outruns docs). Fix pattern: before starting any task gated on another task's status, spend one `git log`/grep to confirm, and flip the checkbox with an "audited YYYY-MM-DD, TASKS.md was stale" note the moment you find the mismatch, in the same commit as whatever work led you to notice.
- **Contradicting doc left unresolved after a deliberate supersession** — a scoping decision gets explicitly reversed by later work, but the original doc's prohibition text is left as-is with no note, so a future reader (human or agent) sees two documents disagreeing with no way to tell which one is current. Fix pattern: when superseding an explicit "don't do X" note, add an inline annotation at that exact spot (not just a separate changelog entry) explaining what changed and why, per CLAUDE.md's "resolve the drift explicitly, never silently" rule.
