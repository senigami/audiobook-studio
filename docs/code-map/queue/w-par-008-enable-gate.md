2026-07-03 — W-PAR 002/008 (the enable-gate): wires 002/003/005's parent/child concurrent fan-out model into the LIVE dispatch path. Before this change, `ChapterSynthesisTask`/`SegmentSynthesisTask` (`app/orchestration/tasks/segment_synthesis.py`) existed fully built and unit-tested but stood alone — the live chapter-render submission path (`app/api/routers/generation.py`) still constructed the sequential `SynthesisTask`, which for `engine_id="mixed"` calls `handle_mixed_job`'s single-threaded per-group loop. This change makes `ChapterSynthesisTask` the live path for any segment-orchestrated engine, with cap=1 (today's manifest default for most engines) remaining byte-identical to the pre-wiring sequential behavior.

**Design constraint from the owner (2026-07-03 rulings), followed exactly:**
- `handle_mixed_job` must NOT become the per-child entry point — routing every concurrent child's mixed-engine render through the FULL handler would re-trigger its chapter-terminal job-status write, stitch, and full-chapter DB rebuild once per child instead of once per chapter (a correctness bug the phase-1 design review caught before implementation).
- `_dispatch_segment`'s existing per-segment isolation (003, INV-6) must be reused for children, not reinvented.
- The chapter-fan-out PARENT must not itself flow through `_dispatch_segment` (would register an idle log_listener and publish a spurious "Loading voice model…" frame for a task that renders nothing).

**`plugins/tts_mixed/handler.py` — `render_one_group` extraction (R1):** the per-group loop body from `handle_mixed_job`'s previous L382-451 (markers, `_render_segment` call, `_is_valid_segment_artifact` gate, `[SEGMENT_SAVED]`, `update_segments_bulk`/`clear_duplicate_segment_audio_paths` for that group's own segments) is now a standalone function `render_one_group(group, chapter_dir, on_output, cancel_check, task_id, safe_mode, *, chapter_id=None, lexicon_entries=None) -> RenderGroupResult`. It does ONLY per-group work — zero chapter-terminal job-status writes, zero stitch, zero chapter-wide DB rebuild — so it is safe to call once per concurrent child. `handle_mixed_job` itself is unchanged in behavior: its sequential loop now calls `render_one_group` per group instead of inlining the same logic, with the loop retaining ownership of the chapter-terminal work (stitch, `_persist_mixed_chapter_output`, final `update_job`).

**`app/domain/chunk_groups.py` — `build_script_entry_for_group` extraction (R2):** the per-group script-entry-building logic (id/ids/save_path/weight/text/engine/speaker_wav/voice_profile_dir) previously inlined in `generation.py`'s `_build_script_for_chapter` loop is now a shared helper both the live chapter-script builder AND the new per-child synthetic-task path call — no duplicate logic.

**`app/orchestration/tasks/segment_synthesis.py` — the real `bridge_call` + `is_chapter_fanout`:**
- `_SyntheticSegmentTask(StudioTask)` — a one-group synthetic task used ONLY to reuse `_dispatch_segment`'s isolation for a single child. `prefers_local_execution` is `engine_id == "mixed"`; its `run()` calls `render_one_group` directly (never `handle_mixed_job`, never the old `SynthesisTask.run()` indirection) when local; `to_bridge_request()` builds a request from the one-group script entry for any other engine (routed through `_dispatch_segment`'s existing bridge branch). Its `cancel_check` (`_is_cancelled`) consults BOTH its own `_cancelled` flag (never set in the concurrent path — nothing calls this object's own `on_cancel()`) AND the shared `stop_event` passed in from its owning `SegmentSynthesisTask` — an adversarial-review fix (see below).
- `make_dispatch_segment_bridge_call(orchestrator) -> Callable[[SegmentSynthesisTask], TaskResult]` — the real `bridge_call` factory. Builds the synthetic task + `TaskContext` from the child's group (via `build_script_entry_for_group`) and calls `orchestrator._dispatch_segment(task=synthetic, context=...)` once. Falls back to the script entry's known `save_path` for `output_path` when `_dispatch_segment`'s bridge-routed branch doesn't set it on the returned `TaskResult`.
- `ChapterSynthesisTask.is_chapter_fanout: bool = True` — checked by `orchestrator_helpers._dispatch`, which now has a one-line branch: `if getattr(task, "is_chapter_fanout", False): return task.run()`, bypassing `_dispatch_segment` for the parent entirely (R4 ruling).
- `ChapterSynthesisTask` gained `safe_mode` and lazily-loaded `_lexicon_entries` (loaded once per chapter, mirroring the sequential handler), threaded to each child via a new `parent_context` dict on `SegmentSynthesisTask` (project/chapter id, voice profile, safe_mode, lexicon).
- `ChapterSynthesisTask._current_active_segments_map()` — genuine multi-entry `active_segments_map` aggregation: one entry per child that has started (`child.finished is False`), keyed by the child's REAL segment/leader id (never the synthetic per-child task_id). Guarded by the SAME `_EMIT_ACTIVE_SEGMENTS_MAP` flag as `orchestrator_helpers.py` (imported from there — single source of truth), now flipped `True`.

**Bug fix found and fixed during this work — recovery stitch data loss (INV-2/INV-8 interaction):** `_fan_out_chapter` previously returned only the constructed children; a group `needs_render_fn` excluded (already valid, recovery K-of-N) never became a child and its existing output path never entered `run()`'s `stitch_entries`. On a real crash-then-restart-with-partial-progress, the final stitched chapter WAV would silently be missing every already-completed segment. Fixed: `_fan_out_chapter` now returns `(children, skip_stitch_entries)`; a new `resolve_existing_output_fn` companion to `needs_render_fn` resolves the already-valid group's existing path, and `run()` seeds `stitch_entries` with these skip entries before merging in newly-rendered children's paths — including the edge case of a FULLY-recovered chapter (zero children to render) still invoking `stitch_fn` once with all N existing paths. Three regression tests in `tests/orchestration/test_correctness_invariants.py::TestRecoveryKofN`, R1 revert-checked.

**`app/orchestration/scheduler/orchestrator.py` — recovery reconstruction:** `_reconstruct_task` gained a branch for `task_type == "synthesis"`: when the recovered payload's engine `uses_segment_orchestration`, it delegates to `_reconstruct_chapter_task_from_context(context)`, which rebuilds the chapter's chunk-group script fresh from the DB (the recovered payload is a bare `processing_queue` row with no `script` field), wires `needs_render_fn`/`resolve_existing_output_fn` to `plugins/tts_mixed/handler.py`'s `_group_needs_render`/`_group_ready_audio_path` (INV-8), and wires a `stitch_fn`/`_stitch_recovered_chapter` that mirrors `handle_mixed_job`'s terminal block (stitch, mark segments done, `_persist_mixed_chapter_output`, final `update_job`). Falls back to the existing `SynthesisTask.from_task_context` path on any resolution failure or non-segment-orchestrated engine.

**`app/api/routers/generation.py` — the live switch:** new `_build_chapter_synthesis_task(...)` factory: for `uses_segment_orchestration(engine_id)`, constructs `ChapterSynthesisTask` with `max_concurrent_workers` derived from the SAME manifest cap each child independently resolves (`_manifest_resource_claim(engine_id).cap`, maxed across a mixed chapter's distinct group engines) — so the parent's own `ThreadPoolExecutor` bound is never a second, lower ceiling than the per-engine-class semaphore; raising ONE manifest's `behavior.max_concurrent_workers` is sufficient to enable visible parallelism, no separate chapter-level knob. `needs_render_fn`/`resolve_existing_output_fn`/`stitch_fn` mirror `is_bake` semantics exactly as `handle_mixed_job` does today. Both `api_add_to_queue` (normal chapter render) and `api_bake_chapter` now call this factory; the segment-scoped "generate these specific segments" endpoint (`segment_ids=sids`, not a chapter-level render) is UNCHANGED — still `SynthesisTask` (out of scope; not a chapter fan-out).

**`_EMIT_ACTIVE_SEGMENTS_MAP` flipped ON** (`orchestrator_helpers.py`) — was OFF since 003/005 to avoid a redundant single-entry map leaking stale `preparing` state at cap=1 on cold starts. Now genuine multi-entry maps exist (real concurrent children), and the cap=1 single-call-site case still only ever emits at most one entry (unchanged shape) — `tests/orchestration/test_dispatch_isolation.py`'s deferred-at-cap1 test was rewritten (`test_single_dispatch_segment_call_emits_one_entry_at_a_time`) to assert this, and a new `tests/orchestration/test_parent_child_scheduling.py::TestActiveSegmentsMapMultiEntryAggregation` proves the genuine multi-entry case with a `threading.Barrier`-forced concurrent overlap.

**Self-adversarial pass findings (fixed):**
1. **`ChapterSynthesisTask._children` race** — the retry-once swap (`_run_child_with_retry`, one call per `ThreadPoolExecutor` worker), the heartbeat monitor thread's iteration, and the new `active_segments_map` aggregation all read/mutate the same plain Python list concurrently with no lock — a retry's index-then-assign (or its except-`ValueError` append) could race a concurrent iterator. Fixed with a `self._children_lock` guarding every access site (all four: `_tick`, `_current_active_segments_map`, `stalled_segments`, the retry swap); readers take a `list(...)` snapshot under the lock rather than holding it during iteration.
2. **Synthetic child cancel gap** — a real chapter cancel only ever calls the PARENT `ChapterSynthesisTask.on_cancel()`; nothing calls each per-child `_SyntheticSegmentTask`'s own `on_cancel()`, so its private `_cancelled` flag (the ONLY thing the OLD `SynthesisTask` design relied on) would never flip during a real cancel. Fixed: `_SyntheticSegmentTask._is_cancelled()` also consults the shared `stop_event` (the same one `SegmentSynthesisTask.run()` already checks before/after admission), threaded in via `make_dispatch_segment_bridge_call`. Residual, documented, NOT fixed (matches pre-existing sequential-path granularity, not a regression): an ALREADY-DISPATCHED `render_one_group`/bridge call in flight cannot be interrupted mid-render — `render_one_group` only checks `cancel_check()` at entry, same granularity as `handle_mixed_job`'s per-group loop today.
3. **Semaphore leak audit** — confirmed `SegmentSynthesisTask.run()`'s `reserve_task_resources`/`release_task_resources` pairing is `try/finally`-safe regardless of what `_bridge_call` (and everything it calls, including `_dispatch_segment`, which itself converts internal exceptions to `TaskResult`s rather than propagating) does; no new resource-acquisition point was added anywhere else in the new code.
